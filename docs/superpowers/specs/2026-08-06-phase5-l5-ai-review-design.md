# Phase 5（L5：AI レビュー）設計

全体設計書は `2026-07-29-multilayer-quality-gates-verification-design.md`。本書はその §9（L5 の 3 ケース）と §10（Phase 5 の完了条件）を、Phase 4 完了時点の実測を踏まえて具体化したものである。実装手順は `docs/superpowers/plans/` の Phase 5 計画に委ねる。

## 1. 目的

手順書 §6（L5：AI レビュー）と §7（cloudbuild）の記述が実際に成り立つかを実測する。検証対象は次の 3 つの主張である。

1. **§0 の設計原則 3**「L5 は L1〜L4 の上に重ねる補助線」——L1〜L4 が全緑になる欠陥が実在し、それを L5 が拾うか
2. **§6.1**「LLM の脆弱性判定は非頑健」——手順書自身がこう書いているので、同一差分・同一プロンプトで指摘が揺れるかを反復実測する
3. **§6.2 のチェックリスト**が §10 で L5 に割り当てられた落とし穴を実際にカバーしているか

## 2. 前提（Phase 4 完了時点で確定している構造）

Phase 5 の設計を縛る実測が 3 つある。

**(1) L4 は触ったファイルで機械的に反応する（§1.53）。** `l4-mutation` は「欠陥を検出した」のではなく「差分に入ったファイルの差分限定スコアが閾値 50 を下回った」だけで fail する。`orders.service.ts` のフル実行スコアは 40 % である。

**(2) `stryker-diff.sh` は `apps/api/src` 配下の非 spec `.ts` だけを見る。** したがって次の非対称がある。

| ケースが触るもの | `l4-mutation` の挙動 |
|---|---|
| `apps/web` 配下のみ | `L4_MUTATE_FILES=(none)` でスキップ（緑） |
| `apps/api/src` の spec のみ | 同上（緑） |
| `apps/api/src` の非 spec | Stryker が起動し、スコア次第で赤 |

**(3) `l3-test` が pass しないケースでは `l4-mutation` を実行しない**（`run-case.sh` の規約。§1.54）。

この 3 つから、**申し送り #39 が想定した「L5-02 を作り直せば L1〜L4 全緑になる」は成立しない**。`apps/api/src` に N+1 を注入する以上 L4 は構造的に反応するし、既存 spec がクエリ形を固定している以上 L3 が先に赤くなって L4 はスキップされる。この帰結自体が記録すべき発見である。

## 3. 決定事項

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| D1 | `l5-ai-review` をハーネスの中で走らせるか | **`GATE_ORDER` / `GATE_DETECTION` の外に置く。** `l3-e2e-web` と同じ扱い | `claude -p` は非決定的で、`RESULTS.md` がバイト単位で不変という性質（判定の信頼性を支えている）を失う。1 回の実行結果を恒久的な事実として表に固定するより、反復実測のほうが情報量が多い |
| D2 | `L5-02` の題材（申し送り #39） | **設計書どおり `orders.service.ts` に N+1 を注入し、既存 spec は触らない。** 赤くなった層を記録する | CLAUDE.md の絶対ルール（判定を `match` にするために `case.patch` を書き換えない）に忠実。§2 のとおり #39 の 2 案はどちらも L4 の反応を回避できず、それが新しい発見になる |
| D3 | Phase 5 に含めるハーネス改善 | **#41 のみ。** #40（`--mutate` の除外再適用）と #27（ルール ID 照合）は扱わない | #41 は「このリポジトリの自動チェックのどれ一つも Stryker が起動できることを確認していない」という検証の信頼性そのものの穴 |
| D4 | nightly ローカル実測の範囲 | **Playwright フル実行と web Stryker の差分限定（#34）。** `FC_NUM_RUNS=10000` は再実測しない | FC の対比は §1.31 で実測済み（100 回 0.344 秒 / 10000 回 0.350 秒）で新情報が出ない。上記 2 つは未実測 |
| D5 | 反復実測の規模 | **同一モデル 5 回 × 3 ケース = 15 実行** | 交絡因子を増やさずに §6.1 の「非頑健」を測れる。n=5 なら 5/5 と 3/5 の区別が付く。モデル間差を混ぜると n=3 では寄与を切り分けられない |
| D6 | 「AI レビューが指摘した」の判定 | **機械判定を主軸にし、生出力 15 本を全部保存する** | 判定基準を後から検証できる。キーワード grep だけでは「該当なし」と書いた行の偽陽性を検証できない |

## 4. 成果物

### 4.1 L5 の実行系

| ファイル | 役割 |
|---|---|
| `.claude/skills/code-review/SKILL.md` | 手順書 §6.2 の逐語。チェックリスト 8 項目と出力形式（`\| 重大度 \| ファイル:行 \| 指摘 \| 根拠 \|`）を含む |
| `scripts/gates/l5-ai-review.sh` | `claude -p "/code-review <base>...HEAD"` を呼び、生出力をファイルへ保存する。`GATE_ORDER` / `GATE_DETECTION` には入れない。exit code は 0 固定（手順書 §6.3 の `\|\| true` に相当）で、`claude` が起動できないときだけ 2 |
| `verification/run-l5.sh` | 3 ケース × 5 回を回し、生出力 15 本を保存 → 機械判定 → `verification/L5-REVIEW.md` を生成する |
| `verification/L5-REVIEW.md` | 反復実測の集計表。`RESULTS.md` には L5 が出ないため、L5 の指摘はここに記録する |

`l5-ai-review.sh` の比較対象は `GATE_BASE_REF` で受け取る（`l2-new-deps.sh` / `stryker-diff.sh` と同じ規約）。

`run-l5.sh` はケースの適用に `run-case.sh` と同じ機構を使う——作業ツリーのクリーンチェック → `verify/<CASE-ID>` ブランチを切る → `case.patch` を当ててコミット → 実行 → 元のブランチへ戻る。5 回の実行は 1 つの検証ブランチの中で回す（ブランチを 5 回切り直す必要はない。差分が同一であることが反復実測の前提だから、むしろ切り直さないほうが正しい）。

**`L5-REVIEW.md` は追跡ファイルなので、`RESULTS.md` と同じ注意が要る。** `run-l5.sh` がこれを書き換えたまま次に `run-case.sh` / `run-all.sh` を実行すると、作業ツリーが汚れているという理由で exit 2 になる。実行後にコミットするか `git checkout` で戻す。

**判定ロジックは 4.2 の実測結果が出てから書く。** 出力形式が組み込みの `/code-review` のものか手順書 §6.2 の表形式かで grep 対象が変わるため、先に生出力を 1 本取ってから機械判定を実装する。

### 4.2 最初に実測すべきリスク

**`/code-review` は Claude Code の組み込みコマンドとして既に存在する。** 手順書 §6.2 が指定する `.claude/skills/code-review/SKILL.md` を逐語で置くと名前が衝突する。**Phase 5 の最初のタスクで、`claude -p "/code-review ..."` が組み込みと SKILL.md のどちらを呼ぶかを実測する。**

組み込みが優先されるなら、手順書 §6.2 の指示は「書いた SKILL.md が読まれない」形で空振りする。その場合は次の 2 つを分けて記録する。

- 手順書逐語（`/code-review`）の挙動——空振りするかどうかの実測結果
- 検証を続けるための回避策——スキル名を変える（例 `/l5-review`）か、`claude -p` にチェックリストを直接渡す

**どちらを採ったかを `L5-REVIEW.md` と findings に明記する。** 回避策の挙動を手順書逐語の挙動として記録してはならない。

### 4.3 L5 系 3 ケース

| ID | 仕込む欠陥 | 触るファイル | `l4-mutation` | 期待される判定 |
|---|---|---|---|---|
| `L5-01-duplicate-logic` | web 側で API の `discountedTotal` を使わず、`@repo/shared` の定数から割引を再実装する | `apps/web/src/features/orders/orderTotal.ts` | (none) スキップ | L1〜L4 全緑 → `not-caught` |
| `L5-02-n-plus-one` | `findByUser` の `include: { user: true }` を外し、注文ごとに `findUnique` でユーザーを引く | `apps/api/src/orders/orders.service.ts` | skipped（`l3-test` が赤のため） | `l3-test` 赤 → `mismatch` |
| `L5-03-missing-boundary-test` | `discount.spec.ts` の境界値 3 件（閾値ちょうど / すぐ下 / すぐ上）を削除する | `apps/api/src/discount/discount.spec.ts` | (none) スキップ | L1〜L4 全緑 → `not-caught` |

`claimed_layer` は 3 件すべて `L5`、`claimed_gate` は `l5-ai-review`。`l5-ai-review` は `actual.tsv` に現れないため `judge()` は `blockedBy` 経路に落ち、`claimGateVerdict` は `mismatch` になる。**これは意図した挙動である**（D1 の帰結）。

`L5-01` と `L5-03` の期待値は「L1〜L4 全緑」だが、`RESULTS.md` の表示は `❌ どの層も止めなかった` になる。§1.26 と同型の「非ブロックゲートは層の枠組みで測れない」構造なので、`RESULTS.md` の注記でこれを説明する。

**`L5-03` は対照フル実行も取る。** 境界値テストを消せば `discount.ts` の mutant が生き残るはずで、差分限定実行が無反応でもフル実行なら L4 が反応する可能性がある。`L4-01`（§1.56）と同型の実測になる。

### 4.4 判定基準（D6）

ケースごとに、対応する §6.2 チェックリスト項目を事前に固定する。

| ケース | 対応するチェックリスト項目 |
|---|---|
| `L5-02` | 「N+1：ORM のクエリが件数に比例して増えないか」 |
| `L5-03` | 「境界値：閾値のちょうど上・ちょうど・すぐ下のテストがあるか」 |
| `L5-01` | **存在しない** |

**`L5-01` に対応する項目が無いことは手順書の穴である。** §10 は「設計の一貫性が崩れ、重複が増える」を `L5 / 人間` に割り当て、具体策として「チェックリスト＋CODEOWNERS」を挙げるが、§6.2 のチェックリスト 8 項目に重複・設計一貫性の項目は無い。`L5-01` では「チェックリスト外の自発的指摘があったか」を別の列で記録する。

集計は 3 列で持つ。

1. **該当項目を「該当」と判定したか**（`L5-01` は n/a）
2. **チェックリスト外の自発的指摘があったか**
3. **偽陽性の件数**——健全な箇所への指摘。手順書 §6.2 の但し書き「gap を探せと指示されたレビュアは健全な成果物でも何かしら報告しがち」の実測にあたる

### 4.5 #41 の修正（D3）

**baseline 側の挙動は変えない。** `run-all.sh` の baseline ループが `GATE_BASE_REF` を export するようにすると baseline が差分ありで Stryker を回すようになり、影響の実測が別途必要になる（#41 の但し書き）。

代わりに `gates.test.sh` に、`apps/api/src` の非 spec を 1 ファイル触った差分を作って `stryker-diff.sh` が**実際に Stryker を起動し mutant を実行する**ことを確認するケースを足す。これで自動チェックが初めて `L4_MUTATE_FILES=(none)` 以外の経路を通る。

### 4.7 cloudbuild yaml（未実行）

`gcloud` が無いため実行しない。`scripts/gates/*.sh` を呼ぶ薄い記述にして「ローカルで検証したものと CI で動くものが同一」を担保する（全体設計書 §10）。

## 7. この設計が守るべき制約（CLAUDE.md より）

- `expect.yml` の `claimed_layer` は絶対に変えない。`expect` の pass/fail は実測に合わせて更新してよい
- 判定を `match` にするために `case.patch` を書き換えない。`mismatch` / `not-caught` が成果物である
- ゲートやスクリプトを足したら、**意図的に違反を 1 つ入れて赤くなることを確認する**。緑の確認だけでは、そのゲートが何も見ていない状態と区別できない
- 新しい層を足したら、既存の全ゲートを回すまで終わりではない（Phase 3 で 4 回、Phase 4 で 2 回、層をまたぐ相互作用が起きた）
- `run-all.sh` は必ずバックグラウンドで実行する（Bash ツールのタイムアウト上限を超える実行を実測している）
